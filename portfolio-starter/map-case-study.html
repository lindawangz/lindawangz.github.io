Save Cantonese World Map Programs

Designing a clearer way for people to find Cantonese learning programs — while helping Save Cantonese move from a developer-dependent update process toward a more maintainable system.

Save Cantonese NOVA F25 Onboarding Project Product Design + Engineering
01 · Context

Start with the people and the problem.

Save Cantonese is a nonprofit dedicated to strengthening the Cantonese-speaking and learning community. Its grassroots advocacy promotes education through local language programs, connects the Cantonese diaspora worldwide, and supports the protection of culture and identity.

The existing World Map was intended to help learners discover Cantonese programs around the world. But the larger challenge was not simply making a map look better: the organization also needed a way to keep program information accurate and current.

The project therefore became a two-sided design problem: make discovery easier for learners, and make updates easier for the people maintaining the map.
02 · The Problems

We had to solve the workflow, not just the interface.

The project brief identified a major operational bottleneck: submissions required R-code knowledge to review and publish. That created delays, a growing backlog, and an inefficient workflow that depended on developers.

Program discovery was difficult Learners could struggle to find Cantonese classes and programs near them, creating a need for a clearer geographic and database experience.
Updates were technically dependent Community-submitted programs could not be easily reviewed and published without technical knowledge.
Information could become outdated The organization needed a more systematic way to verify program websites and keep the public map current.
One view was not enough The experience needed to support both geographic exploration and a structured list of program information.
03 · Process

From client conversations to a workable system.

The design process centered on understanding what Save Cantonese actually needed to maintain the map. Through client conversations, we translated the organization's pain points into concrete product requirements before deciding on the final interface.

01

Understand

Clarify how programs were currently submitted, reviewed, published, and discovered — and where the existing workflow was breaking down.

02

Align with the client

Use client conversations to distinguish the organization's must-haves from interface ideas: reliable data, easier review, and a map that learners could navigate intuitively.

03

Explore

Compare existing map patterns and identify useful conventions for markers, clustering, filters, side panels, and list-based access.

04

Build the system

Connect the public-facing map and table with verification and approval logic so the design addressed both the learner and the organization maintaining it.

04 · Client Alignment

The client conversations shaped the product requirements.

Rather than treating the map as a purely visual redesign, we used client discussions to focus the project on the operational issues behind it. The resulting direction connected what learners needed to see with what Save Cantonese needed to manage behind the scenes.

01
Make program discovery flexible People should be able to browse geographically while also using a table and filters to find specific programs.
02
Reduce dependence on technical review New submissions should pass through a systematic verification and approval flow rather than relying on manual developer intervention for every update.
03
Keep program details connected to location Selecting a program should reveal useful details without forcing the user to abandon the geographic context.
04
Design for information that changes Website verification and a more systematic data workflow became part of the product solution, not an afterthought.
05 · Exploration

Then we looked outward before designing inward.

Competitive analysis helped us decide which map conventions were worth keeping and which patterns would make the experience harder to use.

What we considered: layouts showing multiple programs, target points, geographic clustering, and filters for different categories.

What we wanted to avoid: a single way to access programs, a complicated or nonfunctional sidebar, and removing the list format.
06 · Solution

The solution became a map + database + verification workflow.

The final direction combined a refined public interface with a more systematic process for reviewing and updating submitted programs.

01
Automated verification The system checks whether a submitted program website is live and accessible before the program moves through the approval pipeline.
02
Map + table access Approved programs are represented geographically and in a structured table, giving users two complementary ways to browse.
03
Focused program details A side panel keeps the selected program's details visible alongside the map instead of separating the information from its location.
07 · Interaction Design

Designing the ways people actually search.

The map supports filtering by audience, city, state or province, and country, while markers communicate program categories directly on the map.

09 · Technical Workflow

Designing the experience meant designing the pipeline too.

The implementation connected the interface to a data workflow using Next.js, Tailwind CSS, MapLibre GL, Google Apps Script, and Google Sheets.

This technical approach supported the larger product goal: making the map easier to maintain while keeping the public-facing experience clear and searchable.

10 · Impact

The result was a faster, more maintainable update cycle.

3–5 min Reported total deployment/update time after the new workflow, compared with roughly 2 hours previously.
~34 The deck references 14 Google Form updates and roughly 20 Slack updates addressed through the new automated email workflow.
Nightly The map moved from a previous 1–2 times per year update cadence toward realtime nightly updates with website verification.
11 · Reflection

The biggest design decision was treating maintenance as part of UX.

The project started as a map experience, but the process revealed that the quality of the map depended on the workflow behind it. A useful public interface was only one part of the solution; the organization also needed a repeatable way to verify and update the information users rely on.

That led to a product direction where discovery, filtering, program details, verification, and data maintenance work together instead of being treated as separate pieces.
